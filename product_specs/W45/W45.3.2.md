## Objective

`POST /api/members` rejects any body that is not a valid `Membership` and
returns **all** the problems at once. Valid members are stored with real `Date`
objects.

## Background

Your PR #10 added an email check, and the comment in `server/index.ts` says
full validation is "its own TODO". This is that TODO. Today, anything with an
`emails` array becomes a member, including one with no `name`, a role of
`"Wizard"`, or a `startDate` of `"yesterday"`. The model functions then crash
or quietly misbehave on it later, far from the request that caused it.

There are two TypeScript lessons in here:

- **Types disappear at runtime.** `Role` is a union type, so there is no array
  of roles you can check against when the request arrives. The standard fix is
  to declare the values once as a `const` array and **derive** the type from it.
  That way the list and the type can never disagree.
- **JSON has no dates.** A `startDate` arrives as a string. Chunlin's W45.1.1
  `reviveMember` solves exactly this for the frontend. Reuse it if it has
  landed rather than writing it twice.

## Files you will touch

- `utils/model/types.ts` (the `Role` declaration only)
- `server/validation.ts` (new)
- `server/index.ts` (the `POST /api/members` route only)

## What to change

1. In `types.ts`, replace the `Role` union with a `ROLES` array declared
   `as const` and `type Role = (typeof ROLES)[number]`. Nothing else in the code
   base should need to change. `npm run build` will tell you if it does.
2. In `server/validation.ts`, write `validateNewMember(body: unknown):
   string[]`, which returns a list of human-readable problems (empty means
   valid). Check at least:
   - `name` is a non-empty string.
   - `emails` is a non-empty array of strings that look like emails.
   - `positionHistory` is an array (it may be empty). Every entry has a `role`
     in `ROLES` and a parseable `startDate`. `endDate`, if present, parses and is
     not before `startDate`.
   - `discord`, `github` and `desiredRoles`, if present, have the right types.
     Each `desiredRoles` entry is in `ROLES`.
3. In the route, return **400** with `{ error: string, details: string[] }`
   when there are problems. Keep the existing **409** for a taken email.
4. Before storing a valid member, convert its dates (via `reviveMember` if it
   exists).

## How to approach it

- Collect every problem and return them all. Returning only the first one makes
  the client fix-and-resend one mistake at a time.
- Messages should say where the problem is, e.g.
  `positionHistory[1].role "Wizard" is not a known role`.
- Test with a deliberately bad body that has three mistakes, and check that all
  three come back.

## Acceptance criteria

- [ ] `Role` is derived from a `ROLES` const array, and `npm run build` passes.
- [ ] A body missing `name`, with an unknown role and an unparseable date,
      returns 400 with all three problems in `details`.
- [ ] A valid body returns 201, and the stored member's `startDate` is a `Date`
      (log it once to check).
- [ ] A taken email still returns 409.
- [ ] Your PR includes the `curl` commands you used.
