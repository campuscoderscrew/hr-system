## Objective

Two pure functions answer the HR Committee's most common question, *"who is
free and knows React?"*, without any UI.

## Background

From `features_TODO.md`: search by name, role, team, availability status and
proficiency. Today the answer comes from scrolling.

Writing the logic as plain functions in `utils/model/`, separate from any
component, keeps it out of the view (MVC). It also makes it testable once
Jenny's W45.4.1 lands, and lets the server reuse it later for a
`GET /api/members?role=...`.

Most member facts live on **positions**, not on the member. `availability`,
`proficiency`, `role` and `team` are all fields of a `Position`, and only
**current** positions (no `endDate`) count. `currentPositions()` in `types.ts`
already does that filtering.

## Files you will touch

- `utils/model/search.ts` (new)

## What to change

1. Define a `MemberFilter` type, where every field is optional:
   - `query`: free text matched case-insensitively against name, every
     email, Discord and GitHub.
   - `roles`: keep members holding **any** of these roles currently.
   - `teams`: keep members currently on **any** of these teams.
   - `availabilityStatus`: one or more of `ACTIVE`, `INACTIVE`, `BREAK`,
     `UNKNOWN`.
   - `minProficiency`: e.g. `{ frontEnd: 3 }`, keeping members whose current
     proficiency in that area is at least 3.
2. `filterMembers(members, filter): Membership[]`. Different fields combine
   with **AND**. Values inside one field combine with **OR**. An empty filter
   returns everyone.
3. `sortMembers(members, by, direction): Membership[]` with `by` = `"name"`,
   `"proficiencyTotal"` or `"availability"` (by hours).
4. **Neither function mutates its input.** This is the opposite of
   `operations.ts`, on purpose. The page passes in its real state array, and
   reordering that array in place would be a nasty bug.

## How to approach it

- Decide what `"X"` (unknown) proficiency means for `minProficiency`. "Doesn't
  match" is the safe answer: HR asked who *knows* React, not who might. Write
  the decision in a comment.
- Availability comes in four shapes (`range`, `atLeast`, `lessThan`,
  `hoursUnknown`). Sorting needs one number per member. Pick a rule (for
  example the `min` of a range), document it, and put unknowns last in both
  directions.
- A member can have two current positions with different proficiency. Decide
  whether `minProficiency` matches if **any** position qualifies, and document
  it.
- If Manan's W45.3.2 has landed, use the `ROLES` array for role values.

## Acceptance criteria

- [ ] Empty filter → same members, same order.
- [ ] `{ query: "ada" }` matches "Ada", "ADA" and `ada@umd.edu`.
- [ ] `{ roles: ["Developer"], minProficiency: { frontEnd: 3 } }` returns only
      current developers with front end ≥ 3.
- [ ] Ended positions never cause a match.
- [ ] Neither function mutates its argument (check by comparing before/after).
- [ ] Decisions about `"X"`, multiple positions and unknown availability are
      commented.
- [ ] `npm run build` passes. Add tests if W45.4.1 has landed.
