## Objective

`npm test` runs a test suite. A tiny helper makes building test members a
one-liner, and one real test passes.

## Background

`features_TODO.md` calls this *the highest-leverage item in the file*. Every
W38 spec said "verify by hand with a `console.log`" because the repo has no
test runner. The model code (`utils/model/operations.ts`,
`utils/model/organization.ts`) is made of pure functions over a `Membership[]`
array, which is the easiest kind of code to test.

We are using **Vitest**. It reads the existing `vite.config.ts`, so path
aliases like `@utils/*` should already work, and its API is the same as Jest's,
which most tutorials use.

Two decisions are made for you:

- **Tests do not import `data.ts`.** It is ~5,000 lines of real member data
  that changes whenever HR edits it, so a test that depends on it breaks for
  reasons that have nothing to do with the code. Tests build small members of
  their own.
- **That is what the fixture builder is for.** `makeMember({ name: "Ada" })`
  returns a complete, valid `Membership` with sensible defaults, and you
  override only what the test cares about.

## Files you will touch

- `package.json` (`test` script, dev dependency)
- `vite.config.ts` (only a `test` block, if Vitest needs one)
- `utils/model/testing/fixtures.ts` (new)
- `utils/model/types.test.ts` (new, one smoke test)

## What to change

1. Install Vitest as a dev dependency. **Check the version against our Vite
   version (8.x)** in Vitest's docs or its peer dependencies. A mismatched pair
   is the most likely way this hour goes wrong.
2. Add `"test": "vitest run"` and `"test:watch": "vitest"`.
3. Write `makeMember(overrides?)` and `makePosition(overrides?)` in
   `fixtures.ts`. Defaults should give a unique email per call, so two members
   never collide by accident, and one current position.
4. Write one smoke test for `currentPositions()` from `types.ts`: a member with
   one ended and one current position returns only the current one.
5. Add a short "Testing" section to the README: how to run tests, where they go
   (`*.test.ts` next to the file under test), and "use the fixtures, not
   `data.ts`".

## How to approach it

- Get a test that asserts `1 + 1 === 2` passing first, then delete it. That
  separates "Vitest is set up wrong" from "my test is wrong".
- Make sure `npm run build` does not try to bundle test files. Check with a
  build after adding them.
- `makeMember` should not share objects between calls. If two members share
  one `positionHistory` array, a test that mutates one silently changes the
  other.
