## Objective

After a successful login, the app knows who is logged in and what their user
type is. `/members` is reachable after logging in and redirects to `/login`
when you are logged out.

## Background

This continues your W43 work on `feature/user-permissions` (commit `63c4275`).
The structure there is right: a `UserAuthContext`, a provider, and a
`<Navigate>` guard. Three things stop it from working.

1. **The provider is below the hook that reads it.** `App` calls
   `useContext(UserAuthContext)` and then renders `<UserAuthProvider>` inside
   its own JSX. A component cannot read a context that it is itself providing,
   so `App` always gets the default value. `loginStatus` is always `undefined`,
   and `/members` always redirects.
2. **Nothing ever sets the context.** `login.tsx` checks the password and calls
   `navigate("/members")`, but never calls `setLoginStatus`.
3. **The context holds a `Login`, which includes the password.** A password
   should not be sitting in React state for every component to read.

Also check this before merging: the branch renames `Login` fields from
`Username/Password/UserType` to lowercase. `server/index.ts` (on `main`) still
reads `credentials.Username` in `POST /login`, so the rename silently breaks
the server login. Keep the lowercase names (they match the rest of the code
base) and update the server to match.

## What to change

1. Define a `CurrentUser` type, `{ username, userType }`, with no password.
   That is what the context holds.
2. Move `<UserAuthProvider>` **above** the component that reads it. You can wrap
   `<App />` in `main.tsx`'s `root.render`, or extract the routes into a child
   component. Pick one and explain why in the PR.
3. Expose `login(user)` and `logout()` from the context instead of a raw
   setter, so callers cannot put arbitrary shapes in.
4. In `login.tsx`, call `login(...)` on success **before** navigating.
5. Decide what a page refresh does. Today a refresh logs you out. For Phase 1,
   keeping `CurrentUser` in `sessionStorage` is acceptable, and the password
   never goes there. Write a short comment in the provider saying this is a
   Phase 1 stand-in for the server session.
6. Make the `Login` field names consistent on both sides (see Background).

## How to approach it

- Put a `console.log(loginStatus)` in the guard before changing anything, and
  watch it stay `undefined` after logging in. Then fix the provider order and
  watch it still be `undefined`, because of problem 2. Fixing them one at a time
  shows you which bug caused what.
- Make the guard a small `<RequireLogin>` component rather than a ternary
  inside `<Route>`. W45.2.3 will want a similar one that checks the user type.

## Acceptance criteria

- [ ] Logging in as a valid user lands on `/members` and stays there.
- [ ] Visiting `/members` while logged out redirects to `/login`.
- [ ] The context never contains a password (check with React DevTools).
- [ ] Refresh behaviour matches what your provider comment says.
- [ ] `POST /login` on the server still accepts the documented credentials
      after the field rename. Test with `curl` or a REST client.
- [ ] `npm run build` passes.
