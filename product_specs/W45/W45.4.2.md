## Objective

`utils/model/operations.test.ts` covers the functions the app and the server
actually call: `moveMemberToTeam`, `moveMember`, `addRole`, `removeMemberDeep`
and `updateMember`.

## Background

These functions sit behind every drag, delete and edit, on both the client and
the server. They rest on two rules from the project notes, and those rules are
what the tests should protect:

1. **History is append-only.** A move closes the old position by setting
   `endDate` and pushes a new one. Nothing is ever deleted or overwritten.
2. **The functions mutate the array they are given.** That is why `members.tsx`
   copies the array before calling them. Tests must build fresh data for every
   test, or one test's mutation leaks into the next.

## Files you will touch

- `utils/model/operations.test.ts` (new)

## What to change

For each function, read its code and doc comment first, then write tests for:

- **`moveMemberToTeam`**: the old position gets an `endDate`; a new position
  with the new role/supervisor is added; `positionHistory` gets **longer** by
  one; other current positions are untouched; it returns `null` for an unknown
  email and for a role the member does not currently hold.
- **`moveMember`**: what happens to *all* current positions (read the code to
  find out, then pin the behaviour down in a test).
- **`addRole`**: adds a current position without ending any.
- **`removeMemberDeep`**: removes the member, and clears supervisor references
  to them on other members. Check the returned `clearedReferences` and
  `affectedMembers` counts against a fixture where you know the right answer.
- **`updateMember`**: changes only the fields passed in and never touches
  `positionHistory`.

## How to approach it

- One `describe` per function. Use test names that read as sentences:
  `"closes the old position instead of deleting it"`.
- Build fixtures inside each test or in a `beforeEach`, never at file level.
- If a test reveals behaviour that looks like a bug, **do not fix the
  function.** Write the test for the behaviour you believe is correct, mark it
  `it.todo` or `it.fails` with a comment, and add a line to
  `features_TODO.md`. Fixing model code is outside this spec, and someone may be
  depending on the current behaviour.
- Dates: compare with `toEqual` or `getTime()`, not `===`. Two `Date` objects
  with the same time are not `===`.

## Acceptance criteria

- [ ] Every function listed above has at least one happy-path test and one
      not-found test.
- [ ] At least one test asserts history only grows (append-only).
- [ ] Tests pass when run in any order (`vitest --sequence.shuffle`).
- [ ] Any suspected bugs are logged in `features_TODO.md`, not fixed.
- [ ] `npm test` and `npm run build` pass.
