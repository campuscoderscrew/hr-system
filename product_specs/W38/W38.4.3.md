## Objective

Make deletion actually complete. Right now, removing a member leaves their name
scattered across other members' records as a supervisor who no longer exists.

## Background

From the business spec:

> If this is a current member being removed, we need to remove their data
> everywhere it appears in the system

"Everywhere" is doing a lot of work in that sentence. `removeMember` splices one
entry out of one array. But `Position.supervisor` is a `SupervisorRef` — a
`[name, email]` tuple copied into every subordinate's position. There is a
comment in `types.ts` saying exactly this:

> this is a denormalized copy, not a reference. Nothing links it back to the
> supervising Membership, so if that member's name or primary email changes,
> every Position pointing at them silently goes stale.

Delete a team lead today and every one of their developers still claims to report
to them. `TeamLayout` matches members to positions by comparing
`position.supervisor?.[0] === team.teamLead.name`, so a stale ref does not just
look wrong — it changes which role renders in the cell.

This is the most "backend-shaped" spec of the week. It is data integrity work
that will move to the server in Phase 2 almost unchanged.

## Files you will touch

- `utils/model/operations.ts`
- `src/pages/members.tsx` (to surface the summary)

## What to change

1. Write an audit function first, before changing any behaviour:

   ```ts
   function findReferencesTo(members: Membership[], email: string): {
     member: Membership;
     position: Position;
     kind: "supervisor";
   }[]
   ```

   Every place the given member is referenced by someone else. Run it against
   `data.ts` for a few real team leads and see how many hits you get. That number
   is the point of this spec.

2. Extend deletion so it cleans up. Add a new function rather than changing
   `removeMember` — the Express server in `server/index.ts` imports the existing
   one, and this spec should not break it.

   ```ts
   function removeMemberDeep(members: Membership[], email: string): {
     removed: Membership | null;
     clearedReferences: number;
   }
   ```

3. Decide what "cleaning up" means for a supervisor reference, and document the
   choice:
   - **Clear it** — set `supervisor` to `undefined`. Honest: we no longer know
     who supervises this person. Leaves teams needing reassignment.
   - **Reassign upward** — point the subordinate at their supervisor's
     supervisor. Keeps the chain intact, but invents a reporting line HR never
     approved.
   - **Leave historical positions alone, clear only current ones.** A position
     that ended in 2024 records who supervised it *then*; erasing that is
     falsifying history.

   Our recommendation is the third combined with the first, but argue it out.
   Whatever you pick, write the reasoning in a comment — this is the kind of
   decision someone will question in six months.

4. Handle the team-lead case. If the deleted member was a team's lead, that team
   now has none. `buildOrganization` (W38.1.2) was specified to tolerate a
   leadless team — verify it actually does, with a real delete, rather than
   assuming.

5. Report what happened. After a delete, tell the user what else changed:
   "Deleted Alex Chen. Cleared 6 supervisor references across 4 members." Reuse
   whatever message surface W38.3.4 built if it has merged; otherwise a simple
   banner is fine.

6. Run `getCycles(members)` after a delete and confirm it still returns
   sensibly. It walks `supervisor` edges, so a half-cleaned graph is exactly the
   kind of thing that breaks it.

## How to approach it

- Write `findReferencesTo` and log its output before you write anything that
  mutates. You cannot fix what you have not measured.
- `data.ts` has real supervisor chains in it. Delete "Jane Smith" (who supervises
  John Doe, who supervises her — there is a genuine two-cycle in the seed data)
  and see what happens. That is your test case.
- Remember `emails` is an array. A member may be referenced by a secondary email.
  Match against all of them.
- This function must stay pure of React. It is model code.

## Acceptance criteria

- [ ] `findReferencesTo` is exported and reports supervisor references by any of
      a member's emails.
- [ ] `removeMemberDeep` is exported; the original `removeMember` is unchanged
      and `server/index.ts` still compiles.
- [ ] After deleting a member, no other member's **current** position references
      them as supervisor.
- [ ] Your chosen policy for historical positions is implemented and documented.
- [ ] Deleting a team lead does not crash the spreadsheet; the team renders
      without a lead.
- [ ] `getCycles` runs without throwing after a delete.
- [ ] The UI reports how many references were cleared.
- [ ] `findReferencesTo` returns `[]` — not a crash — for an email nobody
      references.
- [ ] `npm run build` passes.
