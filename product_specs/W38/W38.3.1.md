## Objective

Write the model function that performs a team-to-team move, with no UI involved.
Drag-and-drop is just a way to call this function; the function is where the
business rules live.

## Background

`utils/model/operations.ts` already has `moveMember(members, email, newRole, supervisor)`.
It is not sufficient here, for two reasons:

1. It closes **every** current position the member holds. Moving a Developer from
   Team Whale to Team Lemon must not also strip them of their Treasurer role in
   Finance. It should close only the position being moved.
2. It records no destination. The new `Position` it pushes has a role and a
   supervisor but no `operationsSector`, `department`, `cluster` or `team` — so
   after the "move", the member belongs to no team at all and vanishes from the
   spreadsheet.

The HR process this models is real: the sheet has to answer "where was this
person in October" a year from now. That is why we close the old position with an
`endDate` instead of editing it in place. **History is append-only. Never delete
or overwrite a `Position`.**

## Files you will touch

- `utils/model/operations.ts`

## What to change

Export a new function. Suggested signature — adjust if you can justify it:

```ts
function moveMemberToTeam(
  members: Membership[],
  email: string,
  fromPosition: Position,
  destination: {
    operationsSector?: SectorNames;
    department?: DepartmentNames;
    cluster?: string;
    team?: TeamNames;
  },
): Membership | null
```

Behaviour:

1. Find the member by email. `Membership.emails` is an **array** — some members
   have multiple. Match against any of them. Return `null` if not found.
2. Find the specific current position matching `fromPosition`. Return `null` if
   the member does not currently hold it.
3. Close that position: set its `endDate` to now. Leave every other position
   untouched.
4. Push a new `Position` carrying the destination fields, with `startDate` now.
5. Decide what carries over to the new position and what does not. Write your
   reasoning as comments. Our rules:
   - `role` — carries over. A Developer moving teams is still a Developer.
   - `experienceLevel` — carries over.
   - `proficiency` — carries over. It is a property of the person.
   - `availability` — carries over.
   - `supervisor` — **does not** carry over. New team, new lead. Leave it
     undefined; W38.3.3 will supply the destination team's lead.
6. Bump `member.updatedAt`.
7. Return the updated member.

Also export a validator:

```ts
function canMoveToTeam(member, fromPosition, destination): { ok: true } | { ok: false; reason: string }
```

It should reject at minimum: a no-op move (destination identical to source), and
a member who does not currently hold `fromPosition`. The `reason` string will be
shown to the user in W38.3.4, so write it for a human — "Alex is already on Team
Whale", not `"ERR_SAME_TEAM"`.

## How to approach it

- Read the existing `moveMember` and `addRole` first. Follow their style: same
  JSDoc comment format, same `export { ... }` block at the bottom of the file.
- Comparing positions by object identity (`===`) works if the caller passes the
  exact object it got from `currentPositions(member)`. Comparing by value is
  harder than it looks — `Date` objects are never `===` to each other. Pick
  identity, and document the assumption that callers pass the real object.
- This function mutates the `members` array, consistent with the rest of the
  file. That is a deliberate (if debatable) house style — W38.1.3 knows about it
  and copies the array before calling in. Do not change the style unilaterally.
- Verify by hand: call it from a scratch `console.log`, check that the member has
  one more position, that the old one has an `endDate`, that unrelated positions
  are unchanged, and that `positionHistory.length` grew by exactly one.

## Acceptance criteria

- [ ] `moveMemberToTeam` and `canMoveToTeam` are exported from `operations.ts`.
- [ ] Moving one position of a two-position member leaves the other position
      completely untouched — same `role`, same `endDate` (absent), same object.
- [ ] The closed position keeps its original `startDate` and gains an `endDate`.
- [ ] No `Position` is ever removed from `positionHistory`.
- [ ] The new position carries the destination's sector / department / cluster /
      team, so the member renders in the new team after a rebuild.
- [ ] A member matched by their second or third email works the same as by their
      first.
- [ ] Unknown email returns `null` rather than throwing.
- [ ] `canMoveToTeam` rejects a same-team move with a human-readable reason.
- [ ] Your carry-over rules are documented in comments.
- [ ] `npm run build` passes.

## Out of scope

- Any `.tsx` file. No UI in this spec at all.
- Changing `moveMember` — leave the existing function alone, the server imports it.
- Reassigning `teamLead` when a lead is moved. That edge case is W38.3.4.
