## Objective

Give each member a delete affordance that opens the confirmation dialog and, on
confirmation, actually removes them from the model and the screen.

## Background

`removeMember(members, email)` already exists in `utils/model/operations.ts`. It
finds the member by email, `splice`s them out, and returns them (or `null`).
That is the easy half.

The half that needs thought: **delete is the one irreversible action in this
app.** There is no undo and no backend to restore from. The dialog from W38.4.1
is the only thing standing between a tired HR lead and a member's entire role
history. So the affordance should be discoverable but not adjacent to anything
people click often, and the dialog must show enough for the user to confirm they
have the right person.

## Files you will touch

- `src/components/SpreadsheetLayout.tsx`
- `src/pages/members.tsx`

## What to change

1. Add a delete control to each member's column in `TeamLayout`. A small icon
   button is fine — the project already depends on
   `@fortawesome/fontawesome-free`. Keep it visually quiet: subtle by default,
   clearly red on hover/focus. Give it an accessible label
   (`aria-label={`Delete ${member.name}`}`) since an icon alone reads as nothing
   to a screen reader.

2. Hold the "pending deletion" member in state. `null` means the dialog is
   closed. One piece of state, not a boolean plus a member.

3. Render one `ConfirmDeleteModal` driven by that state. The `description` prop
   should make the consequence concrete — the member's name, their emails, and
   **how many positions in their history will be destroyed**. "Delete Alex Chen —
   this removes 4 positions spanning Aug 2024 to present. This cannot be undone."
   is a real confirmation; "Are you sure?" is not.

4. On confirm: copy the member array, call `removeMember` on the copy, push the
   copy into state, close the dialog. The reference-equality warning from W38.1.3
   applies here exactly as it did in W38.3.3.

5. Verify the member disappears from **every** place they were rendered. A member
   with two current positions shows up in two teams; deleting them must clear
   both. If it only clears one, the bug is in how the tree is rebuilt, not in the
   delete.

6. Decide where the modal is rendered from. Rendering one modal at the page level
   and driving it from state is correct. Rendering a modal inside `TeamLayout`
   means one modal instance per team per member — do not do that, and be able to
   explain why in your PR.

## How to approach it

- Build it in this order: button that `console.log`s → state holding the pending
  member → modal opens with the right name → confirm actually deletes.
- Counting positions for the description is one line with
  `member.positionHistory.length`. Getting the date range is `roleTimeline` from
  W38.2.1 if it has landed, or the min/max `startDate` if not — do not block on
  that spec.
- If the delete button is inside a `draggable` element (W38.3.2), clicking it may
  start a drag instead. If W38.3.2 has merged, test the interaction; you may need
  `draggable={false}` on the button or a `stopPropagation` on `mousedown`.

## Acceptance criteria

- [ ] Every member column has a labelled delete control.
- [ ] Clicking it opens the confirmation dialog naming that specific member.
- [ ] The dialog states how many positions will be lost and that the action
      cannot be undone.
- [ ] Typing `DELETE` and confirming removes the member from state and from the
      rendered spreadsheet with no page refresh.
- [ ] A member who appears in two teams disappears from both.
- [ ] Cancelling changes nothing.
- [ ] Exactly one `ConfirmDeleteModal` is mounted in the tree at a time.
- [ ] The delete control does not trigger a drag (or W38.3.2 has not merged yet,
      noted in your PR).
- [ ] The imported array in `data.ts` is not mutated — a refresh restores the
      member.
- [ ] `npm run build` passes.
