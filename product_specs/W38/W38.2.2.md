## Objective

Build the card itself — the panel that will eventually appear on hover — as a
plain component with no hover logic in it at all.

## Background

Separating "what the card looks like" from "when the card appears" is what makes
this a one-hour job instead of a three-hour one. This spec is the first half.
W38.2.3 is the second half.

A **presentational component** takes props and returns markup. No `useState`, no
event handlers, no data fetching. It renders the same thing every time for the
same props, which means you can develop it by just dropping it on the page and
looking at it.

## Files you will touch

- `src/components/MemberHoverCard.tsx` (new file)
- `src/pages/members.tsx` (temporary scaffolding only — removed before PR)

## What to change

1. Create `src/components/MemberHoverCard.tsx`, default-exporting a
   `MemberHoverCard` component with roughly this prop shape:

   ```ts
   {
     member: Membership;
     currentPosition?: Position;  // the position the member was hovered in
     className?: ClassValue[];
   }
   ```

2. The card renders, in this order:
   - **Header** — member name, and the formatted current role for
     `currentPosition` if one was passed.
   - **Contact** — Discord username, GitHub username, emails. Some members have
     `github: "NONE"` or no `discord` at all. Render a dash, not the string
     `"NONE"` and not `undefined`.
   - **Role timeline** — from `roleTimeline(member)` (W38.2.1). Each entry shows
     the role label and its period. Render it as a visual sequence so the
     progression reads like the business spec's example:
     `Developer (Aug 5, 2024 – Nov 1, 2025) → Primary Lead (Nov 1, 2025 – Present)`.
     A vertical list with connectors or a horizontal chain of chips both work —
     pick one and make it legible at 8+ entries.
   - **Other current roles** — from `otherCurrentPositions(member, currentPosition)`.
     Each shows role, and the department / team it sits in. Hide this whole
     section when the array is empty; do not render an empty heading.

3. Style it with Tailwind, using the `cn()` helper from `src/utils.tsx` the same
   way `SpreadsheetLayout.tsx` does. Match the existing visual language — rounded
   corners, `shadow-md`, light neutral surfaces. It should look like it belongs
   to the same app, not like a different website.

4. The card must have a sensible fixed or max width (a member with eight past
   roles must not stretch it across the viewport) and must not set its own
   `position: absolute` / `fixed`. **Positioning is W38.2.3's job.** If you bake
   positioning in here, the next spec has to undo it.

## How to approach it

- Develop it visible: temporarily render
  `<MemberHoverCard member={members[0]} />` at the top of `members.tsx` so you
  can see it while you build. Cycle the index through several members —
  especially the ones with sparse data — then delete the scaffolding before you
  push.
- Build the markup with placeholder text first, get the layout right, then swap
  in the real helper calls.
- Tailwind v4 is set up in this project via `@tailwindcss/vite`; classes work the
  same as you are used to.

## Acceptance criteria

- [ ] `src/components/MemberHoverCard.tsx` exists and is a pure presentational
      component — no `useState`, no `useEffect`, no event handlers.
- [ ] It uses the W38.2.1 helpers rather than re-deriving the timeline inline.
- [ ] Missing fields (`github: "NONE"`, absent `discord`, empty timeline) render
      as a dash or are omitted — never `undefined`, `null`, or `NONE`.
- [ ] The "other current roles" section is absent, not empty, when the member has
      no other current roles.
- [ ] The card does not position itself.
- [ ] Your PR includes screenshots of the card for at least three members: one
      with a long history, one with multiple current roles, one with almost no
      data.
- [ ] No temporary scaffolding remains in `members.tsx`.
- [ ] `npm run build` passes.

## Out of scope

- Editing member data from the card. It is read-only this week.
