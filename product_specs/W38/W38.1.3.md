## Objective

Make the member data *changeable*. Right now the page renders from a module-level
constant, so nothing on screen can ever update. Move the member list into React
state and re-derive the org tree from it.

## Background

`src/pages/members.tsx` does `import { members } from "../../utils/model/data"`
and renders straight from it. If a drag-and-drop handler mutates that array,
React has no idea anything happened and the screen does not change. This is the
single thing blocking both W38.3 (drag & drop) and W38.4 (delete).

The fix is the standard React pattern: the page owns the data in `useState`, and
passes both the data *and a way to change it* down to the components that need
it.

There is a subtlety worth understanding before you start. Our model functions in
`utils/model/operations.ts` — `moveMember`, `addRole`, `removeMember` — **mutate
the array in place** (`members.push(...)`, `members.splice(...)`,
`position.endDate = now`). React compares state by reference. If you call
`removeMember(membersState, email)` and then `setMembers(membersState)`, React
sees the same array reference and skips the re-render. You will be staring at a
screen that did not update while your `console.log` swears the delete worked.
Every developer hits this once. You are being warned in advance.

## Files you will touch

- `src/pages/members.tsx`
- `src/components/SpreadsheetLayout.tsx` (prop plumbing only)

## What to change

1. In `members.tsx`, replace the hardcoded `team` / `nonDevTeam` / `department` /
   `sector` literals entirely. Delete them. They were scaffolding.

2. Hold the member list in state, seeded from the imported `data.ts` array.
   **Seed it with a copy, not the imported array itself** — otherwise editing
   state silently edits the module, and a page refresh shows stale garbage.

3. Derive the org tree from that state with `buildOrganization` (W38.1.2). Use
   `useMemo` so it is not recomputed on every unrelated render, and key the memo
   on the member state.

4. Render the derived sectors by mapping `OperationsSectorLayout` over them.

5. Add a way for descendants to request a change. Pick one and write two
   sentences in a comment explaining why:
   - **Prop drilling** — pass an `onMembersChange` callback down through
     `OperationsSectorLayout` → `DepartmentLayout` → `TeamLayout`. Explicit,
     verbose, and obvious to read.
   - **React Context** — create a `MembersContext` with the list and an updater,
     consume it in `TeamLayout`. Less plumbing, more indirection.

   Either is acceptable for a tree this shallow. What is **not** acceptable is a
   global mutable variable.

6. Make sure a state update actually re-renders. The reliable pattern with our
   mutating model functions is: copy the array, apply the change to the copy,
   then `setMembers(theCopy)`. Prove it works before you open the PR — add a
   temporary throwaway button that removes the first member, confirm the screen
   updates, then delete the button.

## How to approach it

- Build it in stages and check the page after each: (a) state seeded and
  rendering, (b) `useMemo` added, (c) updater plumbed down, (d) temporary test
  button proves re-render, (e) button deleted.
- If the screen does not update, the first thing to check is whether you handed
  `setMembers` the same array reference it already had.
- Shallow copy (`[...members]`) is enough for the array itself. Be aware it is
  *shallow* — the member objects inside are still shared. That is fine for this
  spec; W38.3.1 and W38.4.3 deal with the consequences.

## Acceptance criteria

- [ ] No hardcoded `Team`, `Department` or `OperationsSector` object literals
      remain in `members.tsx`.
- [ ] The rendered page shows real names from `data.ts` grouped into their real
      sectors, departments, clusters and teams.
- [ ] The member list lives in `useState`; the org tree is derived via `useMemo`.
- [ ] The imported `members` array from `data.ts` is not mutated — after
      interacting with the page, a full browser refresh shows the original data.
- [ ] `TeamLayout` can reach a function that updates the member list, by props
      or by context, and there is a comment explaining the choice.
- [ ] A state change causes a visible re-render (demonstrated in your PR
      description — a screen recording or a before/after screenshot is fine).
- [ ] `npm run build` passes.

## Out of scope

- Drag & drop, delete UI, or hover behaviour. Those specs consume what you build
  here; do not build them.
- Persisting changes anywhere. Refreshing the page resetting everything is the
  correct Phase 1 behaviour.
